**四家共有且语义一致的字段只有三个：时间、金额、对方名称。** 其余全部不一致。

### 1.1 「分类」列是三种不同的东西

| 渠道 | 列名 | 实测取值 | 实质 |
|---|---|---|---|
| 支付宝 | 交易分类 | 餐饮美食 / 交通出行 / 医疗健康 / 日用百货 / 商业服务 | **消费类别**（唯一可直接用的） |
| 微信 | 交易类型 | 商户消费 / 扫二维码付款 / 零钱提现 / 转账 | **支付动作** |
| 招商 | 交易摘要 | 快捷支付 715 / 银联快捷支付 254 / 汇入汇款 54 | **支付通道** |
| 民生 | 摘要 | `财付通-快捷支付-<商户名>` 三段拼接 | **通道 + 动作 + 商户** |

现状把四者合并进 `import_records.channel_category`，再抄进 `ledger_transactions.category`。生产库 2680 笔中「商户消费」1710 笔、「转账」369 笔、「扫二维码付款」243 笔——分类维度已完全退化，且支付宝真正可用的消费类别被同字段的垃圾淹没。

### 1.2 银行侧的「对方行名」是通道标识

民生 105 笔按对方行名分布：

```
55 笔  财付通
44 笔  支付宝
 3 笔  中国民生银行股份有限公司（工资、结息）
 2 笔  中国银联股份有限公司
 1 笔  （空）
```

**99/105（94%）是第三方支付通道代扣。** 招商无此列，只能从对手信息里推断（含「支付宝」79 笔、含「财付通/微信」76 笔，共 155/1189）。

### 1.3 跨渠道重复记账是主流，不是边缘

支付平台账单中由银行卡扣款的比例：微信 182/297（61%），支付宝 76/235（32%）。这些交易在对应银行流水里各有一条记录，是**同一笔钱的两次观察**。

实测匹配（日期 ±1 天、同额）：

| 支付平台侧 | 银行侧 | 命中 |
|---|---|---|
| 微信「民生银行储蓄卡(1595)」55 笔 | 民生「对方行名=财付通」55 笔 | 52/55（94%） |
| 微信「招商银行储蓄卡(4444)」102 笔 | 招商流水 | 94/102（92%） |
| 支付宝「招商银行储蓄卡(4444)」14 笔 | 招商流水 | 14/14（100%） |

**若四份账单直接导入，民生那 105 笔里 99 笔是重复记账。**

### 1.4 未命中的 3 笔揭示了匹配的硬约束

微信侧 3 笔「零钱提现」在民生侧存在对应入账，但未被同额匹配命中：

```
微信提现 100.10  →  民生到账 100.00
微信提现  10.01  →  民生到账  10.00
微信提现 140.14  →  民生到账 140.00
```

差额是微信 0.1% 提现手续费。**跨渠道匹配不能用「同额」做键。** 同时这三笔两侧时间戳相差不到一分钟——在双方都有秒级时间时，**时间比金额更可靠**；招商没有秒级时间，只能退回日期窗口 + 余额链序号。

此外这三笔在民生侧的对方行名分别是「财付通」与「中国银联」，说明**通道标识两侧不一致**，只能作为缩小候选集的辅助信号，不能作为匹配主键。

## 二、结论：账单列不能做表结构

四个渠道四套列，第五个（建设银行、网商银行、广发信用卡，均已在实测数据中出现）还会是第五套。凭证层若继续是「所有渠道列的并集」，每接一个渠道就要加列，且会不断制造 1.1 那样的伪公共字段。

**账单的形状取决于出具方的视角。** 同一笔钱：

- 微信账单说：我从你的民生卡扣了 X 付给某商户
- 民生账单说：财付通从这张卡扣了 X，对方是某商户

两条记录，一个事实。凭证层的正确抽象不是「记录」，而是**某机构对一次资金流动的观察**；账本层才是事实。

## 三、目标模型

### 3.1 凭证层：`import_records`（定位改为「渠道观察」）

```sql
import_records(
  id, batch_id, row_index,
  observer,                    -- alipay | wechat | cmb | cmbc | ...
  -- 四家共有、语义一致
  occurred_at,
  occurred_at_precision,       -- 'second' | 'day'（招商为 day）
  amount_cents,                -- 带符号，统一为「我的钱」视角
  counterparty_name_raw,
  -- 重要但非普遍：埋进 JSON 会立刻要挖出来
  counterparty_account_raw,    -- 支付宝对方账号 / 银行对方账号
  counter_channel_raw,         -- 银行「对方行名」；支付平台为空
  pay_instrument_raw,          -- 支付平台「支付方式」；银行为空（账单即该卡）
  description_raw,             -- 商品说明 / 商品；银行为空
  balance_after_cents,         -- 仅银行；余额校验 + 同日排序
  currency,                    -- 默认 CNY
  status_raw,                  -- 仅支付平台
  -- 去重
  external_id,
  external_id_source,          -- 'native'（支付宝/微信）| 'fingerprint'（银行）
  -- 渠道特有的一切，原样存放，不再为任何渠道加列
  raw_json,
  disposition, transaction_id, match_role, created_at
)
```

变更要点：

1. **删除 `channel_category`。** 它是伪公共字段，四家塞进来的不是一回事。原文各自回到 `raw_json`，由规则分别消费：支付宝那份可直接建议 `category_id`；微信「交易类型」、招商「交易摘要」、民生「摘要」用于判定**交易性质**（transfer / refund / 消费），与分类无关。
2. **删除 `idx_import_records_transaction` 唯一索引**，改为 `match_role`（`primary` | `corroborating`）。多条观察对一个事实是常态而非例外（见 1.3）。
3. **新增 `external_id_source`。** 银行账单无交易号，指纹由 `(observer, 账户, 日期, 金额, 余额, 页内序号)` 构造；招商实测 `(日期,金额,余额)` 有 3 组重复、加对手后仍有 2 组，必须带序号。
4. `occurred_at_precision` 是硬需求，不是装饰：招商 1189 笔全部只有日期。

### 3.2 账本层：`ledger_transactions`

一等字段：`occurred_at` + precision、`kind`（income / expense / **transfer**）、`amount_cents`、`currency`、`account_id`、`payee_id`、`payee_name`（展示快照）、`description`、`category_id`、`category_source`、`note`（**仅用户备注**）。

`kind` 必须现在就扩展 transfer：四家账单**都已明确标出**中性交易（支付宝「不计收支」、微信 `/`、银行的提现/充值/还款摘要），识别成本接近零。生产库现有 369 笔「转账」正混在收支统计里虚增数字。

### 3.3 账户归属

银行账单的账户是确定的（账单就是那张卡）。支付平台账单的账户来自 `pay_instrument_raw` → `import_account_mappings`（0013 已建表，零处使用）。实测支付工具取值 7 种，一次配置即可。复合串（`网商银行储蓄卡(8656)&网商银行福利金抵扣` 等）取 `&` 前主扣款方。

批次级 `bind_import_account`（`imports/mod.rs:544`）降级为「仅对未映射行的临时兜底」，UI 标红。

### 3.4 跨渠道合并规则

候选集：支付平台记录的 `pay_instrument` 指向账户 A ⟺ 银行 A 的记录且 `counter_channel` 为对应通道（辅助信号，允许不一致）。

匹配键按可用精度降级：

1. 两侧均有秒级时间 → 时间窗 ±5 分钟 + 金额差 ≤ max(0.5%, ¥0.02)（覆盖提现手续费）
2. 一侧仅有日期（招商）→ 日期窗 ±1 天 + 同额；同日多笔用银行余额链顺序消歧
3. 命中 → 合并为一个 transaction：**支付平台侧作 primary**（商户名、商品说明最丰富），**银行侧作 corroborating**（提供余额校验与确定的账户归属）
4. 未命中 → 各自独立成交易，标记待人工确认

## 四、PDF 账单处理

两家银行的 PDF 均已验证可解析，方案一致：

- **必须按坐标解析。** `pdftotext -layout` 的纯文本不可用：表格单元格垂直居中，多行内容会错位到相邻记录。改用 `pdftotext -bbox-layout` 取词级坐标，以日期列的词为记录锚点、相邻锚 y 中点为边界重组。
- **列边界从表头 xMin 动态读取**，不得硬编码（招商 6 列 / 民生 11 列，且银行改版会漂）。
- **用余额链自校验**：`balance[i] - balance[i-1] == amount[i]`。实测招商 1188/1188 连续、民生 104/104 连续，可作为解析正确性的硬性验收条件，也用于还原招商的同日顺序。
- **落地方式**：服务端加 `poppler-utils` 调用 `pdftotext -bbox-layout`（已验证），解析逻辑与另两家一样留在服务端。备选是前端 pdf.js 提取坐标后传 JSON，但会把解析逻辑劈成两半。

验证脚本（本机 scratchpad，不入库）：`parse_cmb.py`、`parse_cmbc.py`、`cross4.py`。

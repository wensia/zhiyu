# 知余备份与恢复设计

## 方案决策

SQLite 仍是账本的主存储，git 保存整库二进制快照和校验清单。没有采用按表文本导出：文本可读不等于关系状态可恢复，它容易遗漏 `NULL`、BLOB、视图、约束、外键装载顺序、撤销链和幂等记录。`VACUUM INTO` 生成的原生快照保留完整数据库结构，恢复时无需重新解释业务数据。

应用不保存 GitHub token 或 git 凭据。桌面设置页检测本机 GitHub CLI（包括 macOS Homebrew 常见安装路径）及 GitHub.com 登录态；缺少 `gh` 或未登录时，自动同步、立即同步和原生“立即备份”菜单均保持禁用，并给出安装、登录和重新检测指引。

登录后可以用当前个人账号一键创建私有仓库，或从当前账号具有写权限的非归档私有仓库中选择。应用把仓库克隆到 `app_data_dir/backups/` 下的托管目录，配置 `origin`、分支和仓库级提交身份，再把路径保存到 `app_config_dir/backup.json`。旧配置仍可读取；能够从 remote 识别出 GitHub.com `owner/name` 的有效仓库继续使用，不可识别的配置引导用户重新绑定且不会删除原目录。

空仓库可以直接开始同步。非空仓库必须包含通过格式版本、manifest SHA-256、SQLite `integrity_check` 和 `foreign_key_check` 的知余备份；绑定后强制关闭自动同步，必须先走离线恢复并重启，防止本机数据库静默覆盖远端权威快照。

## 文件布局

```text
backup-repo/
  data/
    ledger.sqlite3   # 当前可信快照
    manifest.json    # 格式、时间、数据库 SHA-256、迁移版本与校验结果
  .staging/          # 生成快照时的同文件系统暂存区

app_data_dir/
  zhiyu.db
  backups/          # 应用托管的 GitHub 备份仓库克隆
  backup-state.json # 三态时间、待推送数、错误、running 与 dirty
  pending-restore    # 请求下次启动离线恢复的标记
  quarantine/        # 被替换旧库及其 SQLite sidecar
```

## 备份流程

原生菜单或设置页的“立即备份”依次执行：在暂存区生成快照；运行完整性与外键校验；按 `database_sha256` 判断数据是否变化；更新 `data/` 并本地提交；只做快进推送；最后 fetch 并确认远端 HEAD 等于本地 HEAD。执行器由全局互斥锁保护，重复触发不会并发执行两个 `VACUUM INTO`。数据库忙或其他备份失败只更新旁路状态，不改变正常记账请求的结果。

状态严格分为三层，并分别持久化：

1. “快照已生成”只说明本机产生了通过校验的 SQLite 快照。
2. “本地已提交”只说明快照进入本机 git 历史；此时磁盘损坏仍会丢失。
3. “远端已确认”说明 push 后回读的远端 HEAD 与本地一致；只有这一层可以称为“已备份”。

待推送数使用 `git rev-list --count <remote>/<branch>..HEAD` 计算；远端分支尚不存在时，把 HEAD 的全部提交计为待推送。

## 自动备份策略

桌面内嵌 router 的最外层中间件观察 `/api/v1`：方法不是 GET/HEAD 且响应为 2xx 时，只把 `dirty` 置为 `true`，绝不在业务请求路径同步执行快照或 git。后台任务收到写入信号后等待 30 秒；期间再次写入会重新计时，到点才调用互斥执行器。每 15 分钟的看门狗会在 `dirty` 仍为 `true` 时补跑一次。启动时重新计算待推送数，若大于零，只尝试补推现有本地提交。

备份执行开始时记录写入代次；若执行期间又发生业务写入，远端确认后仍保留 `dirty=true`，避免把未进入本次快照的新变更误判为干净。用户可以在设置页关闭自动同步，手动“立即同步备份”不受该开关影响。两者都要求 GitHub CLI 已登录、私有仓库绑定有效且没有待恢复门禁；gh 暂时不可用时保留 `dirty` 与待推送计数，重新登录后由看门狗继续补推。

## 桌面设置页与安全边界

`GET /desktop/backup` 返回内联 CSS 与 JavaScript 的自包含页面，不依赖 `apps/web` 或前端构建。页面的配置、状态和触发接口位于 `/desktop/backup/api/*`；备份设置窗口与主窗口都使用内嵌服务的同一个 `http://127.0.0.1:<port>` origin。

必须注意：`zhiyu_api::app()` 的 `csrf_guard` 通过 `.layer()` 挂载，只覆盖调用当时已注册的 API 路由。桌面壳之后用 `.route()` 或 `.merge()` 追加的专属路由不会自动经过它。由于配置接口能修改路径、运行接口能触发进程执行 git，桌面备份路由组必须自行挂 Origin 中间件：所有非 GET 请求的 `Origin` 必须逐字严格等于 `config.public_base_url`，错误或缺失都返回 403。以后新增桌面写端点也不能假定 API 的 `csrf_guard` 会兜底。

## 恢复流程

原生菜单“从备份恢复…”只写入 `pending-restore` 并要求重启。下次启动在内嵌 Axum server 和任何数据库连接创建之前读取清单、核对哈希，将快照复制到生产库同文件系统的暂存路径，再运行完整性与外键校验。旧版本备份只允许按已知迁移版本前缀向前迁移，并在迁移后重新校验；包含未知迁移版本的备份必须拒绝并提示升级应用。

全部预检通过后，旧主库与 `-journal`、`-wal`、`-shm` 整组移入带时间戳的隔离目录，再把已验证副本原子 rename 到生产路径。恢复成功才删除标记并启动服务。

## 三个必须记住的坑

1. 恢复时主库与 `-journal`、`-wal`、`-shm` 必须整组隔离。旧 journal 与新主库错配可能直接损坏数据。
2. 本地 commit 不等于异地备份。只有 push 成功并回读确认远端 HEAD 后，才能显示“已备份”；设置页必须一直分开展示三个状态。
3. 明文数据库一旦推到 GitHub，历史对象无法靠删除当前文件彻底收回。是否加密必须在第一次推送前决定；需要保密时应先使用私有仓库并完成加密方案。
